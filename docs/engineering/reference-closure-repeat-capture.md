# Keep reference Repeat counters out of closure snapshots

This increment is stacked directly on verified open/unmerged [PR #97](https://github.com/Shibukedang27/Kuro/pull/97), exact head `c30212fbfe01813ea1d370ff990fd54a929279e5`, with all eight checks successful. Keep the new review PR open and unmerged. **Strict independence remains unfinished.**

## The defect and the narrow repair

The [previous direct-call cleanup repair](reference-repeat-cleanup.md) saves and restores hidden Repeat counters across Action invocations, but `MakeClosure` copied those counters into a closure's capture dictionary. `Invoke` reads its immutable capture/parameter overlay before globals, while Repeat initialization and increments write globals. A closure created during a loop could therefore read the creator's stale hidden counter forever, or skip its own body when that stale counter already met its count. Save/restore alone cannot make an immutable captured counter mutable.

For example, this source compiles on the parent but exceeds an externally imposed instruction budget:

```text
Action Worker Dummy: Integers;
Repeat 2;
Print 7.
Done.
Return 0;
Done.
Repeat 1;
Call MakeClosure "Worker";
Handle = @_;
Call Invoke Handle, 0;
Done.
```

The repaired reference interpreter prints exactly two lines containing `7` and finishes. Creating a handle inside Repeat and invoking it after the creator loop has finished is covered separately.

The only production change is in [`compiler/interpreter.py`](../../compiler/interpreter.py): after combining the global environment and active parameter/capture frames, `MakeClosure` excludes keys matching exactly `__repeat_i[1-9][0-9]*$` (a literal terminal dollar sign). Those are the hygienic counter names generated by [`lower.py`](../../compiler/lower.py); the source lexer cannot spell them. Filtering after the complete merge also prevents an active frame from reintroducing private counters into a nested snapshot. Existing live global counters are not deleted or mutated by capture.

This is a binding-ownership correction, not a scoping redesign. Compiler-private counters remain shared implementation storage with the existing invocation-local SAVEVAR/RESTOREVAR protocol. A newly created closure no longer adds an immutable overlay for that storage, so callee initialization, reads and increments see the same live global binding. Normal completion and explicit Return still restore the caller's counter using the previous repair. No opcode, bytecode format, lowerer, native backend, frame limit or count rule changes.

`Index` is deliberately **not** filtered. It is source-visible capture data under the existing policy. Ordinary variables, similarly spelled source names such as `__repeat_i1`, parameter precedence, captured object references and writes to shared globals retain their existing semantics. No Invoke-time mutation or wholesale capture exclusion is introduced.

## Bounded evidence

[`test_closure_repeat_capture.py`](../../tests/runtime/test_closure_repeat_capture.py) contains eighteen reference-only cases. Every source witness compiles through the normal pipeline and executes with a 10,000-instruction external trace budget. The runner requires empty Action frames and exact restoration of pre-existing dollar-suffixed global bookkeeping, with no newly leaked such bindings.

The cases cover immediate and escaped closure invocation; repeated caller loops; early Return; two nested counter depths with pre-existing global state; a closure calling a direct Repeat-owning Action; closure creation inside an invoked closure; recursive Invoke; delayed Spawn/Await; zero-count loops; ordinary source-name and parameter precedence; immutable captured user reads despite global writes; and seven exact-name/near-name cases. The recursive fixture uses a declaration-only binding populated after snapshot creation, so it does not conflate this fix with an immutable captured placeholder or the result-register overlay.

Running the final tests against the exact parent interpreter in a separate process, without changing the worktree, gives **11 failures and 7 passes**. Failures include bounded instruction exhaustion, an incorrectly skipped body, and assertions that private counter keys must not be retained. The same final module passes all eighteen cases with the repair. These counts are regression evidence, not a claim of cross-runtime closure parity.

One explicit compatibility witness captures `Index = 2`, invokes a callee whose Repeat would otherwise start at zero, and returns the captured `2`; the pre-existing global `Index = 41` is restored. This intentionally records the unresolved source-visible overlay semantics instead of claiming to repair them. Another witness reads captured `Shared = 5` throughout two iterations, while repeated writes leave global `Shared = 6`, preserving the existing snapshot/global-write distinction.

## Boundaries and next path

- **Reference source-created closures only.** The new cases execute the IR interpreter, not a direct-native Action or Kuro-authored closure runtime. BytecodeVM currently lacks SAVEVAR/RESTOREVAR execution; it is not a Repeat acceptance path for this increment. Other engines and native closure representation are unchanged. Inherited authored-runtime gates establish their existing loop contracts, not these new closure semantics.
- **Index and ordinary overlays remain immutable.** A captured `Index`, an Action parameter named `Index`, or a captured result register `_` can still take read priority over loop/call writes to globals. Ordinary captured-variable writes also retain their previous behavior. The filter does not claim general lexical scope, mutable captures, complete Index parity or general closure-program termination.
- **No external-closure migration.** The repair is at `MakeClosure` creation. Host-injected or previously constructed `ClosureValue` objects containing private counter keys are not rewritten on Invoke. Compiler-private names are outside source syntax; compatibility with manually constructed private IR/capture dictionaries is not promised.
- **No error-path unwind or new resource guarantee.** Runtime errors still bypass emitted Return cleanup. Existing recursion/Invoke limits, scheduler behavior, count validation and storage limits remain unchanged.
- **No direct-native cleanup claim.** Direct-native Action SAVEVAR/RESTOREVAR support remains a separate boundary; native artifact launchers execute the authored VM and are not evidence of direct-native Action parity. Keep the earlier compiler loop-flag workaround.

The next narrow runtime step should establish explicit, bounded contracts for source-visible `Index` and result-register ownership during Invoke, then choose a scoped binding/overlay protocol before changing their behavior across engines. Do not simply make all captures mutable or filter every source-visible name. Separately, resume indexed-storage entry/backedge/exit facts and collection control flow, full analyzer/compiler/runtime bytecode admission, Kuro-built native images and a repository-owned object/executable writer. None of those independence milestones is completed by this counter-capture fix.
