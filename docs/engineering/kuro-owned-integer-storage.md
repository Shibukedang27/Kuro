# First bounded integer storage in the Kuro-owned generator

The actual Kuro-written generator, itself built for Linux x86-64, can now turn a narrowly restricted integer collection program into executable Linux x86-64 assembly. This is production lowering, not a Python reference model or a successful run through the Python-authored native emitter. It is deliberately **not** general collection support, macOS generator execution support, full-analyzer integration, or strict toolchain independence.

This increment is stacked directly on verified, open/unmerged [PR #91](https://github.com/Shibukedang27/Kuro/pull/91), exact head `4dae7ed77a12ca56c653ceffc00c53d99aa7ae77`, which passed all eight checks. No merge is authorized.

## What is accepted

An isolated whole-program capability path in [native_codegen.kuro](../../self_host/native_codegen.kuro) recognizes a prefix of fixed integer collection initializers, followed by a straight-line integer stack program. It bypasses the existing general scalar-kind inference pipeline rather than teaching that pipeline to treat a collection pointer as a scalar integer.

The initialization prefix is one to sixteen distinct owners. Each owner has at least two elements; all owners together have at most **32 integer cells**. `BC_MULTI_BEGIN`, two or more `BC_CONST` values, and `BC_STORE_MULTI name` form each initializer. The two-element minimum preserves the authored VM's multi-store contract. Initializers are unsigned ASCII decimal literals of at most four digits. Valid leading-zero decimal spellings are normalized before emission so assembler octal notation cannot reinterpret their values.

After the prefix, the accepted operations are small signed integer constants, checked integer `+`, `-` and `*`, scalar assignment/load, indexed `GET`, `SET`, and integer printing. Up to sixteen scalar names, including the compiler-generated `_` result slot, are admitted. Scalar reads must follow assignment. At least one print and a balanced final operand stack are required. Programs remain limited to **4,096 flat tokens**. Names are compared as data and replaced with numbered labels; user names are never interpolated into assembly.

The signed literal form has one to four ASCII decimal digits and an optional leading minus. Initializer negatives, arithmetic initializer expressions, division, Text and Decimal values, append, length, reassignment, aliases/copies, unindexed collection reads, Actions/parameters/captures, branches and loops are rejected with no emitted assembly. This is a whole-program restriction: existing unrelated scalar programs retain their existing backend, but a program using the new collection representation cannot mix it with those excluded features. Both the **generator execution target** and its **assembly output target** must explicitly be `x86_64-linux`. Either macOS ABI, or unverified execution metadata, rejects collection input before entering the new parser/helpers. Output ABI alone does not qualify an execution host.

`native_codegen_source` and the Python-free shell composer default execution metadata to `unverified`. The image builder resolves the actual image ABI once and uses that same value for both source metadata and image construction. Shell composition can qualify the image explicitly with `sh bootstrap/compose-native-source.sh codegen x86_64-linux x86_64-linux`; that metadata must match the target used to build the generator. This transports an ABI fact, not foreign collection analysis or a fallback compiler.

## Storage and bounds

Every owner gets a separately labelled writable `.data` region containing exactly its initializer values. Scalar slots live in separately labelled `.bss` words. The native operand stack is separate from both. The representation's element kind is fixed to signed integer; its owner, logical length and the aggregate capacity bound are proven by the Kuro-authored emission pass. There is no mutable runtime length word because no admitted operation changes the shape, rebinds an owner, or transports a collection value. The maximum admitted element offset is 248 bytes. Capacity is an admission limit, never a substitute for an owner's logical length.

For length `L`, GET accepts `-L <= index < L`; a negative index is normalized once by adding `L`. SET requires `0 <= index < L` and never grows the collection. Both check before scaled memory addressing. Missing owners and unsupported representations fail during generation; a bad runtime index exits with status 1 and does not execute subsequent instructions. A two-element owner rejects index 2 even if another owner follows it in memory.

Addition, subtraction and multiplication check signed 64-bit overflow and exit with status 1 rather than wrap into a valid index. This is a bounded-integer capability, not arbitrary-precision parity. Endpoint tests construct `INT64_MAX` with overflow-free base-256 Horner arithmetic and `INT64_MIN` by subtracting it from zero, then subtracting one. Separate print witnesses prove the endpoint computations actually succeed; bounds tests therefore cannot pass merely because an earlier calculation overflowed. Separate tests exercise arithmetic overflow itself.

## Evidence and review

[The executable tests](../../tests/self_host/test_native_integer_storage.py) compile source through the Kuro-authored compiler stages, send the resulting bytecode to a freshly native-built actual Kuro generator, assemble/link its output with Clang, check for no undefined symbols, and execute it. Each native execution records source, generator, assembly and executable hashes and exact output/exit status in the test artifact directory. The bootstrap generator seed still comes from Python-hosted compilation; this is not a self-building toolchain.

The bounded indexed-state witness uses two sixteen-cell owners: sixteen mask lanes and a **4-by-4**, sixteen-cell flattened snapshot space. Scalar calculations choose positions, SET mutates the selected cells, and GET proves selected and untouched cells retain distinct values. It is not the earlier sixteen-by-sixteen snapshot witness, which still uses unsupported append operations and remains rejected.

Coverage includes first/last positions, valid negative GET, invalid negative SET, logical one-past-end, signed endpoints, independent owner lengths, internal-looking names, 32/33 aggregate cells, sixteen owners, sixteen/seventeen scalar slots, malformed/truncated bytecode, unsupported element/index kinds and mutation forms, token ceilings, target rejection and scalar Text operands that happen to spell collection opcodes. Integer successes and bounds failures are compared against the hosted interpreter, JSON-round-tripped bytecode VM and Kuro-authored VM where relevant.

Parent inspection corrected four early implementation gaps before final validation: dispatch must scan opcode positions rather than literal/name operands; the new path must retain the token ceiling; the numeric scalar-assignment table is zero-based, unlike the Text-backed metadata tables; and literal limits must count digits after the sign. Inspection also rejected singleton multi-store and validated ASCII integer spellings. The first independent review requested preserving accepted leading-zero source integers rather than restricting their spellings: initializers and signed body literals now remove leading zeros before assembly emission, preserving decimal values, with dedicated source/runtime and signed raw-bytecode regressions.

The first endpoint gate exposed an **inherited Kuro expression-lowering defect**: `Value = 0 - (2 + 1)` produces a second `BC_BINOP +` instead of subtraction. The hosted interpreter returns `-3`; the authored compiler/VM returns `3`. An executable boundary test records that discrepancy rather than calling it successful native parity. This increment implements the stated bytecode contract; it does not establish arbitrary source-expression parity or silently repair the lowering stage. Endpoint and overflow witnesses first store the nested positive computation in a scalar, then apply subtraction/multiplication to scalar operands, and verify the resulting native values explicitly. Fixing recursive operator scratch-state preservation is a separate next-step candidate.

The first normalization implementation conditionally concatenated digits into an initially empty Text value. It worked in hosted execution but the native-bootstrap representation retained an empty length and emitted zeros. Independent review blocked it; the complete superseded run recorded **32 failed, 1,693 passed, 20 skipped**. Those failures were not waived. The repaired helper validates ASCII digits, accumulates a numeric value bounded by 9,999, and uses the existing decimal formatter before applying a nonzero negative sign. Invalid length stops accumulation immediately; oversized raw literals cannot feed unbounded values to the formatter. The complete storage module passes **96 tests** with a fresh native generator, including every decimal digit in initializer and executable positions.

Other superseded full/focused runs were deliberately interrupted when the test set and normalization guard changed; their partial counts are not final-head evidence.

Independent review **approved the bounded bytecode scope**, inspected the exact validity guard, and independently reproduced **96 passed** in the original storage module. The reviewer confirmed the normalization formatter receives only 0..9999, including malformed and oversized tokens; no general source-expression or independence approval is implied.

## Next safe step

Preserve this backend as a bounded executable base. Before allowing loops or branches, prove that every collection owner is initialized before every access, that scalar kinds and stack shapes agree on every path, and that mutation preserves fixed owner/length identity. Before append or reassignment, introduce explicit reviewed logical-length/capacity state and initialization/reset rules rather than inferring length from neighboring allocation or zero-filled storage. Shared identity, parameters/captures, Text and Decimal elements need their own representation and ABI proofs.

Full analyzer execution still exceeds other artifact/storage boundaries; its existing rejection witnesses remain in place. Python-hosted bootstrap seeding and an external assembler/linker are still required. **Strict independence remains unfinished.**
